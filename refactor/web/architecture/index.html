3. Pattern architetturali

3.1 Server Components first

Tutte le pagine di dati sono React Server Components che eseguono le query Supabase direttamente nel corpo della funzione. force-dynamic è necessario su tutte le pagine con dati personalizzati per utente.

// Page.tsx — Server Component
export const dynamic = "force-dynamic";

export default async function MyPage() {
  const supabase = await createClient();       // client SSR cookie-based
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) redirect("/login");

  const { data } = await supabase.from("table").select(...);
  return <ClientComponent initialData={data} />;
}

3.2 Client Components per interattività

I componenti che gestiscono stato locale, form e chiamate API fetch sono Client Components, con suffisso Form.tsx o Client.tsx.

3.3 Route Handlers (API REST)

Ogni handler: (1) autentica con requireTenantUser(), (2) valida il body con Zod, (3) esegue la query Supabase, (4) risponde con NextResponse.json().

async function requireTenantUser() {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return null;
  const { data: profile } = await supabase
    .from("user_profiles")
    .select("role, tenant_id, is_active")
    .eq("id", user.id)
    .maybeSingle();
  if (!profile?.is_active || !profile.tenant_id) return null;
  return { supabase, profile, user };
}

4. Sicurezza e multi-tenancy

4.1 Row Level Security (RLS)

Ogni tabella ha RLS abilitato. L'isolamento tenant è garantito da funzioni PostgreSQL SECURITY DEFINER che evitano ricorsione:

-- Helper functions (evitano ricorsione RLS su user_profiles)
CREATE FUNCTION public.current_user_tenant() RETURNS UUID ...
CREATE FUNCTION public.current_user_role()   RETURNS TEXT ...
CREATE FUNCTION public.is_super_admin()      RETURNS BOOLEAN ...

Le policy applicano il filtro tenant_id = current_user_tenant() su ogni tabella. Il super_admin bypassa tutto tramite is_super_admin() = TRUE.

4.2 Field-level guard (trigger)

tenants_guard_protected_fields

Impedisce ai tenant_owner di modificare status, plan_id, plan_expires_at.

user_profiles_guard_protected_fields

Impedisce agli utenti di modificare il proprio role o tenant_id.

Questi trigger sono un secondo livello di difesa oltre alle RLS policy.

4.3 Macchina a stati del Middleware

Request
  ├─ Path statico o /api/ → pass-through
  ├─ Utente non autenticato
  │   ├─ Rotta pubblica → accesso
  │   └─ Rotta protetta → redirect /login?redirectTo=...
  └─ Utente autenticato
      ├─ Profilo non trovato o is_active=false → signOut + redirect /login
      ├─ super_admin su /dashboard → redirect /admin
      ├─ tenant_user su /admin/* → redirect /dashboard
      ├─ onboarding_completed=false → redirect /onboarding
      └─ tenant sospeso → redirect /account-sospeso

Il middleware usa supabase.auth.getUser() (non getSession()) per validare il JWT contro il server auth ad ogni request — best practice Supabase SSR.

4.4 Auth trigger database

Un trigger PostgreSQL on_auth_user_created crea automaticamente una riga user_profiles alla creazione di ogni utente in auth.users. Legge metadati opzionali (tenant_id, role, full_name) da raw_app_meta_data, consentendo al flusso admin di pre-configurare il profilo a creazione.

6. Architettura dell'integrazione AI

L'AI è integrata esclusivamente nell'import contabile. Il modello viene invocato lato server (Route Handler), mai dal browser. Progettata per rispettare il budget di esecuzione Vercel Hobby (60 secondi per function).

6.3 Struttura del prompt Gemini

Sistema a regole deterministiche basato sulle norme del codice civile italiano:

SP_A

Stato Patrimoniale Attivo

Immobilizzazioni, crediti, liquidità, ratei

SP_P

Stato Patrimoniale Passivo

PN, debiti banche, fornitori, erario

CE

Conto Economico

Ricavi, acquisti, personale, oneri finanziari

F.do

Fondi amm.to

Fondi ammortamento e rettifica

Ottimizzazione token: le voci vengono compattate in oggetti {c, n, v} (codice, nome, valore) prima di essere inserite nel prompt, riducendo drasticamente l'utilizzo.

8. Flusso di autenticazione (dettaglio tecnico)

Browser → POST /auth/signin (Supabase SDK)
  ↓
Supabase Auth → emette JWT + refresh token
  ↓
Supabase SSR → setta cookie HttpOnly
  ↓
Next.js middleware (su ogni request)
  ├─ createMiddlewareClient() → crea client che legge cookie
  ├─ supabase.auth.getUser() → valida JWT contro server auth
  ├─ Legge user_profiles da DB (non da JWT claims)
  └─ Applica routing logic
Il profilo utente (ruolo, tenant, stato) è sempre letto dal database a ogni request nel middleware, mai dai claims JWT. Questo previene che profili modificati (es. disattivati) rimangano attivi fino alla scadenza del token.

10. Decisioni architetturali rilevanti

10.1

Perché Route Handlers invece di Server Actions?

  • Testabilità: le route possono essere chiamate da client, test, strumenti esterni
  • Disaccoppiamento: il client component non dipende da "use server"
  • Compatibilità Vercel Hobby: i Route Handler sono più prevedibili nel comportamento di timeout
10.2

Perché tenant_id denormalizzato?

  • Le policy RLS eseguono per ogni riga — un join aggiuntivo sarebbe costoso
  • Semplifica le policy: tenant_id = current_user_tenant() senza subquery
  • PostgreSQL può usare indici su tenant_id direttamente
10.3

Perché AI solo lato server?

  • Sicurezza: la chiave Gemini non è mai esposta nel bundle client
  • Controllo costi: il server applica rate limiting e rispetta la quota del piano
  • Budget timeout: gestibile solo server-side
10.4

Perché il layout PDF ha priorità sull'output AI?

I PDF di bilancio italiano seguono uno schema fisico standardizzato. I parser rilevano la sezione (SP_A, SP_P, CE_R, CE_C) dal contesto visivo, che è intrinsecamente più affidabile di un'inferenza linguistica. L'AI mappa le voci civilistiche fini, non la classificazione macro.
